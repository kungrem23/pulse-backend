## Исторический этап

Go-реализация подготовлена 2026-10-13. В `cmd/api` подключены PostgreSQL
PhotoRepository и S3 adapter к media service и чтению анкеты. SQL намеренно
оставлен плейсхолдерами по поручению владельца: T08 ожидает заполнения запросов
и проверки с реальными PostgreSQL/MinIO. OpenAPI остаётся `partial`.

## HTTP

- `POST /api/v1/photos`: user access JWT, `multipart/form-data` с одним `file`
  и одним `position`. Порядок частей любой. Поле `user_id`, неизвестные и
  повторяющиеся поля отвергаются. Успех — 201 `{id, url, position}`.
- Полное содержимое JPEG/PNG/WebP проверяется декодированием; MIME и расширение
  файла не определяют формат. Файл до 10 MiB включительно, позиция 1–5.
  Для ограничения памяти декодирования действует технический предел 25 млн
  пикселей; превышение даёт 415. Multipart body до 10 MiB + 64 KiB, включая
  заголовки, boundaries и epilogue; проверяется и неизвестная длина тела.
  Временные файлы при разборе запроса не создаются.
- Неверный multipart — 400; неверная позиция — 422; слишком большой файл/тело —
  413; неподдерживаемое/обрезанное изображение — 415; занятая позиция — 409;
  отсутствие профиля — 409 `profile_required`.
- `DELETE /api/v1/photos/{photo_id}` проверяет UUID и владельца из JWT.
  Успех — 204 без тела; неверный UUID — 400; чужой/отсутствующий файл — 404.
  Повтор после успешного удаления также возвращает 404.
- `GET /api/v1/profile` читает только свои фото в порядке позиций и получает
  свежие URL через S3 на каждом запросе. После удаления последнего фото профиль
  сохраняется, ответ содержит `photos: []`. `SearchState.CheckEligible` для
  такого состояния возвращает `ErrNoPhotos`; фактическое применение в ленте
  и свайпах относится к T09/T10.

Ни один ответ не содержит отдельного поля object key или внутренних ошибок.
Недоступность БД/S3 и неудачная компенсация дают общий 500.

## SQL-плейсхолдеры

Заполнить только константы в `internal/repository/postgres/photo.go` согласно
схеме `decisions_002`. Схема и исторические миграции не менялись.

| Константа | Параметры | Результат |
| --- | --- | --- |
| `createPhotoQuery` | ID, user ID, object key, position | Одна вставленная строка; без upsert/перезаписи позиции |
| `photoByIDForUserQuery` | photo ID, user ID | `id::text, user_id::text, object_key, position`; оба ID в WHERE |
| `photosByUserIDQuery` | user ID | Те же столбцы, только этот владелец, `position ASC` |
| `deletePhotoQuery` | photo ID, user ID | Удаление метаданных; оба ID в WHERE; ноль строк = ErrNotFound |

Адаптер переводит unique violation в `domain.ErrConflict`, FK при вставке —
в `domain.ErrNotFound` (application сообщает `profile_required`), отсутствие
чужого/удалённого фото — в `domain.ErrNotFound`. Ограничения position 1–5 и
UNIQUE(user_id, position) в существующей схеме защищают пять позиций при
конкурирующих запросах. Не заменять вставку на перезапись занятой позиции.

Для пользовательского HTTP-сценария нужны также ранее оставленные запросы
UserRepository, RefreshSessionRepository и ProfileRepository. При пустой
константе метод явно возвращает `SQL query is not written yet` внутри сервера,
клиент получает обобщённый 500.

## Частичные сбои

При загрузке сначала сохраняется объект и получается URL, затем пишутся
метаданные. Ошибка URL или записи метаданных вызывает удаление нового объекта
с отдельным timeout 5 секунд, даже после отмены HTTP-запроса. Ошибка очистки
не скрывается за 409 и становится 500; автоматической очереди уборки нет.

Удаление идёт S3 → PostgreSQL. При отказе S3 метаданные остаются. При отказе
SQL после успешного S3-delete повтор того же DELETE завершает удаление
метаданных; S3-delete идемпотентен. До повтора метаданные могут ссылаться на
уже удалённый объект. Фото/анкету нельзя считать двумя частями одной транзакции.

Неоднозначный сетевой отказ после записи в БД или неудачная компенсация могут
потребовать сверки метаданных и объектов на тестовом/целевом окружении. Здесь
нет обещания распределённой атомарности или восстановления после падения
процесса; durable cleanup/outbox не реализован.

## Проверки

Обычные тесты проверяют validation, MIME/содержимое, ровно 10 MiB, границу
multipart body, JWT ownership, компенсацию, удаление с повтором и выдачу URL.
`TestPhotoHTTPFlowAndConcurrentPositions` проходит router → реальные app services
→ тестовые потокобезопасные адаптеры; восемь загрузок в одну позицию дают один
успех и семь конфликтов, оставляя один объект. Это не доказательство SQL-гонок.

После заполнения SQL:

1. На отдельном тестовом PostgreSQL задайте `PULSE_TEST_DATABASE_URL` с правом
   создания БД. `pgtest` создаёт уникальные базы, применяет обе миграции и
   удаляет только эти базы после теста.
2. Для изолированного MinIO задайте `S3_ENDPOINT`, `S3_PUBLIC_ENDPOINT`,
   `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`. Не используйте production bucket.
3. Выполните команды ниже. Credentials не должны попадать в коммит или логи.

```sh
go test ./...
go vet ./...
go test -race ./internal/app/media ./internal/app/profile ./internal/transport/http/...
go test -count=1 ./internal/repository/postgres ./internal/transport/http/tests
go test -count=1 -tags=integration ./internal/transport/http/tests -run TestPhotosWithPostgresAndS3 -v
git diff --check
```

Реальный тест проверяет upload/read по подписанному URL, конкурентную позицию,
пять фото, отказ шестой/занятой позиции, чужое удаление, повторный DELETE,
очистку объектов компенсации и сохранение анкеты без фото. Он пересобирает
router/services при запросах и тем самым проверяет отсутствие process-local
состояния. Cleanup удаляет только созданные этим тестом ключи. Без нужных env
integration-тест пропускается; с заполненными env и пустым SQL должен падать.
